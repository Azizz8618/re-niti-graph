# Сложные фигуры графопостроителя: набор тестов `verify/figures/`

## Назначение

Соседние наборы `verify/drawings/` (10 простых рисунков, 2–4 точки) и
`verify/benson-commands/` (одна контрольная дека с эталонными хэшами)
проверяют сам факт работоспособности тракта. Этот набор проверяет,
что тот же тракт выдерживает **много различных координат и длинные
программы**: 10–28 пар `MOVE`/`PLOT` на деку, 6 дек, 12 прогонов.

Фигуры выбраны так, чтобы нагружать разные режимы движения:

| Дека | Фигура | Что нагружает |
|---|---|---|
| f01-star | пятиконечная звезда, R=400/r=160, центр (500,500) | чередование длинных и коротких лучей, оба знака X и Y |
| f02-circle | правильный 24-угольник, R=300 | монотонный обход, 24 мелких шага |
| f03-spiral | архимедова спираль, 3 витка, r=20..450 | долгое изменение радиуса, самоподобные витки |
| f04-sine | два периода `Y = 300 + 150·sin`, X=50..950 | частая смена знака приращения Y |
| f05-grid | 5 горизонталей + 5 вертикалей | 20 кадров, возвраты к тем же координатам X/Y |
| f06-sawtooth | 25 точек, Y=200/700 | 24 резких излома, максимальные перепады Y |

## Состав

Все новые файлы находятся только в `verify/figures/` и этом документе:

- `f01-star.b6` … `f06-sawtooth.b6` — деки с **явными** числовыми
  `CALL MOVE(x,y)` / `CALL PLOT()`;
- `gen_decks.py` — генератор (_math_ + _os_, без внешних зависимостей):
  считает координаты заранее, проверяет диапазон `X ≤ 5000`, `Y ≤ 7500`
  и уникальность точек, пишет деки и `expected.tsv`;
- `expected.tsv` — машиночитаемый контракт: число точек, maxX, maxY,
  ожидаемые `width = maxX + 2`, `height = maxY + 1`;
- `run.sh` — раннер: по два прогона на деку, все проверки и итоговая таблица;
- `EXPECTED.md` — ожидаемые признаки и объяснение, почему SVG не идеален;
- `RESULTS.md` — фактические хэши, размеры, воспроизводимость.

## Почему длинные деки теперь работают

Исторически `fortran/verify/PDEV.mad` захардкожил адрес COMMON `/PDEVXY/`
(`0o3147`). С ростом пула констант COMMON уезжал, кадр декодировался в
`(0,0)` и SVG получался пустым. Сейчас `fortran/PLOTSTUB.FTN` вызывает
`CALL PDEV(FRAME(1))`: адрес кадра приходит аргументом, `PDEV.mad` сохраняет
его в R11 и восстанавливает перед каждым ЭК. Поэтому число различных
координат и длина программы не ограничены захардкоженным адресом.
Подробности — `verify/drawings/EXPECTED.md`.

## Как запускать

```
cd /home/azizz/Yandex.Disk/re-niti-graph
DISPAK_BIN=/home/azizz/Yandex.Disk/dispak/build/dispak/dispak \
TMPDIR=/var/tmp KEEP_WORK=1 ./verify/figures/run.sh
```

Переменные:

| Переменная | Назначение | Значение по умолчанию |
|---|---|---|
| `DISPAK_BIN` | бинарник dispak | `/home/azizz/Yandex.Disk/dispak/build/dispak/dispak` |
| `NITI_2348` | рабочая копия диска 2348 с PERSO-библиотекой | `~/.besm6/2348` |
| `TMPDIR` | корень временных каталогов | `/var/tmp` |
| `KEEP_WORK` | если задан, рабочий каталог не удаляется | не задан (удаляется через `trap`) |
| `REF2148`, `TIMEOUT`, `VERBOSE` | вспомогательные | как в `verify/drawings/run.sh` |

Каждый прогон получает
`BESM6_DUDKA_TEST=1 BESM6_DUDKA_PLOT=benson BESM6_DUBNA_PLOT_KEEP=1`
и `BESM6_PATH=<workdir>/disks`. Раннер не меняет файлы репозитория вне
`verify/figures/`, не создаёт `.bak`, не делает git commit/push.
Если пересборка decks нужна, запускают `python3 gen_decks.py` из этой же
папки; он перезаписывает только деки и `expected.tsv`.

## Что именно проверяет `run.sh`

1. Наличие бинарника, дисков, эталонного 2148, дек и `expected.tsv`;
   честная проверка маркера `BESM6_DUDKA_PLOT` в бинарнике: без собранного
   бэкенда результатом будет FAIL, а не выдуманные артефакты.
2. Для каждого раунда (r1, r2): `NITI: summary`, `КОНЕЦ ЗАДАЧИ`,
   отсутствие `ОШ` / `ОШИБКА` / `ERR` / `ОТСУТСТВУЕТ`.
3. `plot.dat` непуст.
4. `benson.out` непуст; каждая непустая строка полностью совпадает с
   шаблоном команды `065xx` (шесть разрешённых кодов) и несёт пометку
   `[аналог NASA, БЕНСОН-501]`. Фактический бэкенд пишет 4-значные коды;
   шаблон принимает и ведущий ноль.
5. `benson.svg`: первая строка `<?xml`, наличие `<svg`, **ровно** ожидаемое
   число `<path>`, `width`/`height` в пределах ожидаемого bbox ±2.
6. Побайтное совпадение SHA256 `plot.dat`, `benson.out`, `benson.svg`
   между r1 и r2.
7. Итоговая таблица: `CASE, SUM, END, NOERR, PLOT, OUT, SVG, CMD, PATH,
   BBOX, DET` и три SHA (12 символов), затем полные SHA256.

Критерий набора: минимум 6 PASS. Файл `summary.csv` и детали лежат в
рабочем каталоге (при `KEEP_WORK=1`).

## Доказано / гипотеза

**Доказано этим прогоном (факты):**

- FOREX 4.12 компилирует все шесть дек, включая 28 пар `MOVE`/`PLOT`
  (f03, f04) и 20 пар координат (f05); в логах нет ошибок.
- Число кадров в `plot.dat` и число `<path>` в SVG равны числу `PLOT`
  (10, 24, 28, 28, 20, 25 соответственно).
- Наблюдаемые `width`/`height` совпадают с `maxX+2` / `maxY+1`,
  предсказанными из координат дек (допуск ±2 в раннере не потребовался).
- Каждая строка `benson.out` — одна из шести команд 065xx с обязательной
  пометкой аналога; посторонних строк нет.
- При двух независимых прогонках каждой деки три артефакта побайтно
  совпадают (детерминированность на этой связке бинарник + диск + дека).
- Движение в SVG действительно Manhattan: каждый наклонный отрезок
  разложен на горизонталь и вертикаль, первый штрих идёт из `(0,0)`,
  ось Y инвертирована.

**Гипотеза / не проверено этим набором:**

- Что реальный БЕНСОН-501 под НИТИ интерпретировал бы эти коды именно так;
  `benson.out` — аналог по NASA TM-76182, а не протокол НИТИ.
- Что реальный графопостроитель провёл бы сплошную линию там, где модель
  даёт лестницу из L-штрихов: это свойство текущего декодера/рендерера,
  а не измеренное поведение железа.
- Что те же SHA воспроизведутся на другой сборке dispak, другом образе
  2348 или после правки побайтного содержимого деки. Хэши привязаны к
  конкретной тройке «бинарник + диск + дека» и эталоном не объявлены.
- Что выбранные радиусы/периоды «лучше» других: это тестовые входные
  данные, а не рекомендация по геометрии.

## Ограничения

- Диапазон координат порта: `X = 0..5000`, `Y = 0..7500` (шаг 0.1 мм).
  Все фигуры лежат в `X = 50..950`, `Y = 88..833`; выход за лимит
  декодером не моделируется как ошибка теста.
- `PLOT()` применяет `INT`, поэтому дробные координаты теряются;
  деки используют целые значения `.0`, чтобы избежать потерь в углах.
- Один кадр — одна точка, один `<path>`. Число штрихов ограничено только
  числом точек: у f05-grid `benson.out` ~957 КБ на 20 кадров.
- SVG хранит координаты в шагах 0.1 мм без масштабирования в мм;
  подписи осей и легенда не генерируются.
- Раннер не сравнивает хэши с жёсткими эталонами из
  `verify/benson-commands/`: эталон там один (C1-line), а здесь
  проверяются внутренняя согласованность и воспроизводимость.

## NASA-оговорка

Коды в `benson.out` (`6501`, `6502`, `6504`, `6511`, `6512`, `6514`)
и пометка `[аналог NASA, БЕНСОН-501]` взяты из модели NASA TM-76182
(сентябрь 1980) и являются **аналогом** для БЕНСОН-501. Это не подлинный
протокол НИТИ/БЭСМ-6. Первичный источник и границы применимости описаны
в `docs/BENSON-COMMAND-FORMAT.md`.
