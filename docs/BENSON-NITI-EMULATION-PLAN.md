## 0. Цель и критерии готовности

Цель: получить в `dispak` воспроизводимую имитацию полного контура НИТИ, от загрузки ДУДКИ по Э50 1216 до физического моделирования шаговых двигателей и пера, с честным разделением «доказано» и «гипотеза», и с выходными артефактами, сравнимыми с уже существующими эталонами.

Под «имитация работает» понимается совокупность условий:

1. Guest-видимый контур трассируется: `РЕГ '34'` (как маски), `РЕГ '240'` (данные), `УВВ 155/164/165/166/4102`, КУС с битом 27, два буфера с переключением, событие 18 вместо подмененного guest-вектора `обвнп1+30`.
2. Есть модель устройства: координаты X/Y в шагах 0.1 мм, перо up/down, лимиты 50 × 75 см, лог со строками, читаемыми человеком: `DUDKA: PEN ... X,Y`.
3. Есть разбор 16-битных элементов `печшк3` и преобразование в команды `+X/-X/+Y/-Y/UP/DOWN`, при этом гипотетические части помечены, таблица разбора настраивается.
4. `plot.dat` по-прежнему записывается в неизменённом формате и даёт те же SHA для существующих дек; дополнительно создаётся новый текстовый лог, по желанию SVG-рендер офлайн.
5. Прерывания и синхронизация описаны честно: guest-вектор в C не моделируется, предлагается минимальный hook на уровне состояния и `eraise()`.
6. Прогнал тестов: низкоуровневые ЭК, контроль ДУДКИ `b1-*`, нативная библиотека 22 + прослойка, Фортран-порт, сверка SHA `plot.dat`, отрицательные тесты.

Критерий приёмки всей работы: дек, выбирающий схему 1216 и управляющий `РЕГ '34'`/`РЕГ '240'`/ЭК 01213, даёт `plot.dat` с N кадрами по 64 строки (1600 байт на кадр) со стабильным SHA и лог со строками `DUDKA: PEN ... X,Y`, координаты монотонны и лежат в 50 × 75 см, при этом все 52 ctest и 6 low-level тестов t01..t06 проходят с прежними SHA. Ни один гипотетический элемент не выдаётся за доказаный.

### 1.3 Чего не хватает

1. **Семантика `РЕГ '34'` не исправлена.** Текущий лог называет 9 слов «инициализацией Бенсона», тогда как по `rukava.be:404,536` это маски ПРП/ГРП. `DU_F_E18` выставляется в `du_reg34_write()` как часть «INIT», хотя прерывание разрешается отдельно через `ТВ67`. Нужно разделить понятия «загрузка масок» и «разрешение прерывания».
2. **`УВВ 4102` не перехватывается.** В `devices[]` (`extra.c:371-373`) есть `0155, 0166, 0164, 0165, 04023`, но нет `04102`. `УВВ 164/165` логируют только номер устройства, не байт из аккумулятора и не состояние кольцевого буфера `0330..0377`.
3. **Нет `ФИЗОБМ` с битом 27 КУС.** Реальный `пв ФИЗОБМ` это подпрограмма гостя, для C-эмулятора невидимая. Существующий ЭК 01213 честно помечен как тестовый hook, а не как подлинный перехват. Нужно добавить отдельный hook с аргументом КУС и проверкой бита 27 (`е27гп`).
4. **Нет физической модели.** Нет координат, шагов, пера, лимитов 50 × 75 см, лога, читаемого человеком.
5. **Нет разбора 16-битных элементов.** Нет таблицы декодирования `печшк3`, каналы `+X/-X/+Y/-Y/UP/DOWN` не формируются.
6. **Нет guest-вектора и масок прерываний.** Не моделируются подмена `обвнп1+30` через `рег '101'`, `ТВ67/ТВ67А`, `ПРП 19`, `ШГ`. `eraise(1<<17)` в `extra.c:363` безусловен при передаче кадра.
7. **Нет второго.output потока.** `plot.dat` единственный артефакт, нет лога и SVG.

### Фаза 2. Модель устройства

Владение (предложение): `dispak/dispak/extra.c`, секция рядом с `du_*` состоянием (`extra.c:68-110`). Новый `struct` не требует изменений в `cu.c`/`optab.c`.

Структура (предложение, имена и типы):

```c
struct benson_device {
    int  x, y;          /* шаги 0.1 мм, начальная точка 0,0 */
    int  pen_down;      /* 0 = UP, 1 = DOWN */
    int  step_x, step_y;/* номинальный шаг в 0.1 мм, по умолчанию 1 */
    int  limit_x, limit_y; /* 5000 и 7500 шагов (50 × 75 см) */
    unsigned long steps;   /* всего шагов, для лога */
};
static struct benson_device ben;
```

Обновление на командах:

| Команда | Действие | Проверка |
|---|---|---|
| `+X` | `x = min(x + step_x, limit_x)` | при упоре лог `DUDKA: LIMIT X` |
| `-X` | `x = max(x - step_x, 0)` | при нуле лог `DUDKA: LIMIT X` |
| `+Y` | `y = min(y + step_y, limit_y)` | при упоре лог `DUDKA: LIMIT Y` |
| `-Y` | `y = max(y - step_y, 0)` | при нуле лог `DUDKA: LIMIT Y` |
| `UP` | `pen_down = 0` | нет движения |
| `DOWN` | `pen_down = 1` | нет движения |

Лог: `DUDKA: PEN DOWN X=00100 Y=00200 (mm 10.0,20.0) step=1`, `DUDKA: PEN UP X=... Y=...`. Формат фиксируется один раз и используется в Фазе 4.

Оговорка о факте: шаг 0.1 мм и число шин (пять) из NASA TM-76182 для Электроники-1001. Для советского Бенсона под НИТИ это перенесённая модель, в логе помечать как `[аналог NASA]`, пока не найдена схема интерфейса.

Контрольная точка фазы 2: детерминированная дека выдаёт шесть команд и лог содержит шесть строк с ожидаемыми координатами, при попытке выйти за лимит координата остаётся на границе.

### Фаза 3. Разбор 16-битных элементов (`печшк3`)

Владение (предложение): `dispak/dispak/extra.c`, новая функция рядом с `niti_frame()`; таблица декодирования задаётся константой в том же файле или подключается через env `BESM6_NITI_DECODE` без жёсткой привязки к формату файла на этом этапе.

Что есть факт (по коду):

- `G10236` (`benson.be:275-282`): `сда 64(М14)`, маска `016(...)` нет, маска `0177777`, тег `D10115 = 060000`, `C1 = ((S & 060000) << 3) | 001377`, упаковка сдвигами `<<2, >>13, <<18, >>14, <<16`.
- Кольцевой буфер 40 слов `0330..0377`, запись `G10207`, байтовая выдача `G10216`: `и П377`, `нтж П377`, `увв '164'`, `сда 64+8`, `увв '165'`.
- Семантика `S` (16-битного элемента) как «13 бит нагрузки + 2 бита класса + 1 бит» это гипотеза по аналогам (`BENSON-PROTOCOL.md` раздел 2). Прямого описания формата команд Бенсона периода НИТИ не найдено.

Что делать:

1. Выделить биты элемента: `payload = w & 0177777`, `class = (w >> 14) & 3`, `marker = (w >> 15) & 1`. Пометить в комментарии: раскладка гипотетична.
2. Завести таблицу `decode[]` вида `{class, marker, action}`, где `action` одна из `ACT_XPLUS/XMINUS/YPLUS/YMINUS/PEN_UP/PEN_DOWN/NOP`. Значения по умолчанию взять из CalComp-аналога (`BENSON-PROTOCOL.md` раздел 5: б0 +X, б1 -X, б2 +Y, б3 -Y, б4 перо вверх, б5 перо вниз) и NASA-команд `6502/6514/6501/6504/6511/6512`. Каждая строка таблицы помечается тегом `[аналог]`.

### 2.5.3. Подмена вектора

Что делается в `dudka.be:120-126`, по порядку:

1. `сч обвнп1+30; зп СТАРОЕ`: старое слово ячейки вектора сохраняется в `СТАРОЕ` (`dudka.be:241`).
2. `сч ЗАМЕНА`: в аккумулятор загружается адрес метки `ЗАМЕНА`.
3. `рег '101'`: запрет приписки. По `rukava.be:540` это режим «БЕЗ ПРИПИСКИ», парный `рег '107'` это разрешение приписки (`rukava.be:541`, используется в `dudka.be:135` и `:228`). Guest пишет слово вектора целиком, без механизма приписки.
4. `зп обвнп1+30`: в ячейку вектора кладётся адрес `ЗАМЕНА`.
5. `ЗАМЕНА мод БНСО; пб ВХОД-ДУДКА` (`dudka.be:242-243`): по подменённому вектору управление попадает не сразу в обработчик, а на модифицируемую команду перехода с базой БНСО.
6. Восстановление в `ВЫХОД`: `сч СТАРОЕ; рег '101'; зп обвнп1+30` (`dudka.be:220-222`), после чего `рег '107'` снова разрешает приписку (`:228`).

Несоответствие «18-й против 31-го разряда». Комментарий в `dudka.be:121` называет `обвнп1+30` «вектором 31-го разряда ГРП», тогда как прерывание от Бенсона разрешается по биту 18 (`dudka.be:163-165`, `сч E18; пв ТВ67`). Это разные системы отсчёта: номер разряда ГРП 18 против индекса ячейки `+30`, который в комментарии назван 31-м разрядом. Прямого объяснения, почему вектор Бенсона лежит именно в ячейке `+30`, в исходниках нет. Выдвигать объяснение как факт нельзя; в разделе 3 это фиксируется как открытый вопрос с пометкой `[гипотеза]` для любого предполагаемого соответствия.

Моделирование без guest-таблицы. В dispak один общий обработчик `ehandler` на все события, а не таблица на 48 линий: `e53()` принимает `011` = адрес обработчика (`extra.c:1163-1166`), `012` = маска `emask` (`:1167-1169`), `013/014` = запрет/разрешение `eenab` (`:1170-1175`), `021` = подъём или сброс событий (`:1201-1205`). `cu.c:144-188` по `goahead` сохраняет 11 слов контекста по `ehandler-11..ehandler-1`, обнуляет `eenab`, ставит `reg[016] = pc = ehandler`, `acc.l = emask`, `acc.r = events`. Возврат из обработчика guest делает через ЭК `015` (`extra.c:1124-1152`), который восстанавливает `eenab = 1`. Guest-таблицы `обвнп1` в C нет и не планируется.

Минимальный hook (предложение, не guest-механизм): завести в `extra.c:68-110` поля `du_vector_slot` (по умолчанию 30), `du_vector_original`, `du_vector_replaced`, `du_prp19`, `du_shg`; ЭК `01215` с подкомандами `set slot`, `install stub`, `restore slot`. Операция `install stub` может вызывать тот же путь, что `e53()` case `011`, то есть писать `ehandler = ADDR(acc.r)` из тестовой деки. Все сообщения об этом обязаны содержать `guest vector обвнп1+30 NOT modeled`, а сам hook нигде не называться «эмуляцией прерывания ДУДКИ».

### 2.5.5. Как это отразить в dispak

Точки в C, где происходит моделирование:

- `extra.c:1155-1212`, `e53()`: `011` задаёт `ehandler`, `012` задаёт `emask`, `013` обнуляет `eenab`, `014` восстанавливает `eenab`, `021` через `eraise()` поднимает или сбрасывает событие. ЭК `015` (`extra.c:1124-1152`) это возврат из обработчика с восстановлением `eenab`.
- `extra.c:3667-3672`, `eraise(uint newev)`: `events |= newev & 0xffffff; goahead |= ehandler && eenab && (events & emask)`. Для бита 18 надо передать `1u << 17`, как уже делает `extra.c:363`.
- `cu.c:144-188`: вход в обработчик при `goahead && !right`. Сохраняются 11 слов по `ehandler-11..ehandler-1`, `eenab = 0`, `reg[016] = pc = ehandler`, `acc.l = emask`, `acc.r = events`, `events = 0`. Это единственный путь перехода, guest-вектор в нём не участвует.
- `extra.c:68-110`: состояние `du_*`. Добавить `du_grp18`, `du_prp19`, `du_shg`, `du_vector_slot`, убрать выставление `DU_F_E18` из блока девяти масок (шаг 1.1).
- `extra.c:330-364`, `dudka_frame_xfer()`: разделить безусловный `eraise(1<<17)` на функцию, вызываемую при `du_grp18 && (du_flags & DU_F_E18)`. Лог: `DUDKA: IRQ event 18 raised (guest vector обвнп1+30 NOT modeled)` и при подавлении `DUDKA: IRQ suppressed (TV67A mask cleared)`.
- «Пробуждение задачи» (`сч E37; или ШГ; зп ШГ; пб БПУ`, `dudka.be:287-294`) в C не воспроизводится. Эмулятор может только поднять event 18, после чего guest-программа, установившая обработчик через ЭК `011`, сама решает, что делать. В логе оставляется `DUDKA: SHG E37 set, task wakeup NOT modeled`.
- «Переключение буфера» (`D10157`, `D10160`, `dudka.be:281-286`) уже есть как `du_buf_active ^= 1` в `extra.c:359`. Нужно дополнить строку лога явными именами: `DUDKA: buffer switched to N (D10157=N D10160=D10161)`.

Что остаётся строкой `NOT modeled` и не эмулируется:

- Запись в guest-ячейку `обвнп1+30` и режимы `рег '101'`/`рег '107'` приписки (`dudka.be:120-126`, `:220-222`, `rukava.be:540-541`).
- `ТВ67/ТВ67А` как аппаратная маска ГРП 18; в C это только булевы флаги `du_grp18`.
- `УСТПРП Е19`, переписывание слова `ОБВНП3+24-19` и чтение `УВВ 4102` с разрядом E13 как аппаратная цепочка (`benson.be:157-162`, `:251-260`).
- `сбр ЧЕРЕЗ1` как аппаратная операция, `ШГ` и `пб БПУ` как диспетчерские действия (`dudka.be:266`, `:287-294`).
- Guest-таблица `обвнп1` и любая привязка события к конкретному разряду ГРП; в dispak один `ehandler` на все события.
