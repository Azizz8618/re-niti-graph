# Вызов графопостроителя по схеме НИТИ: протокол и тесты

Подробное описание того, как программа БЭСМ-6 добирается до графопостроителя
при **непосредственном (локальном) подключении** по схеме НИТИ им. Александрова,
и как этот путь воспроизведён в нашем стенде на базе `dispak`.

Исходная предпосылка (принятая по указанию): удалённая машина и Э50 133
рассматриваются позже; здесь подключение считается прямым. Разбор удалённого
варианта остаётся в `PHYSICAL-LEVEL.md`, раздел 3.

---

## 1. Участники и общая схема

```
программа (Фортран / МАДЛЕН)
   |  CALL PLOT / CALL PAGE / CALL РАGЕ(...)
   v
библиотека 22 (ГРАФОР-СУД)      <- вычисляет координаты, НЕ управляет пером
   |  общие блоки *GFBFTR*, *GFATRN*, *GFBLAN*, *GFNTCH*, *GFGOBS*
   |  внешние точки входа зоны 0o1163: PLOT, PEN, FRAME, PAGE, ENDPG, ...
   v
системный модуль ТРУБКА         <- принимает экстракоды ГП (1200..1217)
   |  gпнити: выбор схемы НИТИ, ТБУФ, КУС, ФИЗОБМ
   v
драйвер ДУДКА                   <- «БЕНСОН», регистры '34'/'240', прерывания
   |  вдудку, ФИЗОБМ, два буферных листа
   v
графопостроитель БЕНСОН         <- физическое устройство
```

Ключевой факт: **в библиотеке 22 нет кода привода пера**
(`PHYSICAL-LEVEL.md:37-47`). Например, в `MOVE1.mad:37` стоит `PLOT :,SUBP,`
(объявление внешней процедуры), а в `MOVE1.mad:206` вызов `13,VJM,PLOT`.
То есть `PLOT`, контракт с системным драйвером, а не тело в библиотеке.

Связка «ТРУБКА -> ДУДКА -> БЕНСОН» зафиксирована прямо в исходниках:
`benson.be:112-114` «РАБОЧИЙ ВАРИАНТ ТРУБКА->ДУДКА->БЕНСОН»,
`dudka.be:345` `БЕНСОН ВНЕШ БЕНСОН,ошибка,вдудку`,
`benson.be:366` `ВХОД ошибка,вдудку`,
`dudka.be:7-10`: модуль загружается из ТРУБКИ по ЭК 1210 (или 1216/1217)
через `gпнити`.

Таблица `rukava.be:3028-3039` (дословно):

```

Э50 1201   ГРАФОПОСТРОИТЕЛЬ: ПОДГОТОВКА К ОБМЕНУ
Э50 1202   ГРАФОПОСТРОИТЕЛЬ: ...
Э50 1203   ГРАФОПОСТРОИТЕЛЬ: ...
Э50 1204   ГРАФОПОСТРОИТЕЛЬ: ЗАПИСЬ НА ТАБЛО
Э50 1205   ГРАФОПОСТРОИТЕЛЬ: ГРАФИК
Э50 1206   ГРАФОПОСТРОИТЕЛЬ: БЕНСОН   (в графе источник стоит ?)
Э50 1207   ГРАФОПОСТРОИТЕЛЬ: БЕНСОН (ЗАХВАТ)
Э50 1210   ЭКСТРАКОД ОБМЕНА С НЕСТАНДАРТНЫМ ОБОРУДОВАНИЕМ
Э50 1216   ГП НИТИ (ДОП. ОБОРУДОВАНИЕ, ВАРИАНТ К-71)
Э50 1217   ГП НИТИ (ДОП. ОБОРУДОВАНИЕ, ВАРИАНТ К-71)
```

Все коды принимает модуль **ТРУБКА** (`trubka.be:1-6`: «МОДУЛЬ ТРУБКА,
ОБСЛУЖИВАНИЕ ГРАФОПОСТРОИТЕЛЯ... А ТАКЖЕ ПОДДЕРЖКА РАБОТЫ ЧЕРЕЗ К-71»),
загрузка `trubka.be:7` `ТРУБКА START '10000'`, база `trubka.be:16`
`УПОТР ТРУБКА(М7)`.

Важное уточнение по 1206: трассировка (см. `PHYSICAL-LEVEL.md`, раздел 4)
доказала, что это **не графика**, а запрос архивной бобины с печатью
`УСТ.СР.К.N БХХХХ` на терминал. Путь: `Э5200 -> ЭК1206 (trubka.be:316-317)
-> БОБН (550-580) -> ВЫДТ1 (586-587) -> ТВ40`. Кадры ГП по 1206 не идут.

Для НИТИ используются коды **1210 / 1216 / 1217**; кадр выводится через
ЭК 1211 (в реальной ОС, через `ФИЗОБМ`, в нашем эмуляторе, через
обработчик 1211).

Сами точки входа вторичного каталога (`PLOT`, `PEN`, `FRAME` и другие)
дизассемблированы отдельно, итоги находятся в `SECONDARY-CATALOG.md`.

### 2.1. Точный экстракод входа в ДУДКУ: Э50 1210

Правильный код входа в ТРУБКУ и ДУДКУ это **Э50 1210**, а не Э52. Запись
«ЭКСТРАКОДА Э52 1210» в шапке `dudka.be:8` является только комментарием.
В машине код `052` означает COS: `dispak/dispak/cu.c:811-813`
(`case 052: err = elfun(EF_COS)`) и `rukava.be:3050` («Э52 0000 | COS»).
Dispatch подтверждён кодом `vzu.be:2180-2185`:

```
ТРУБ    сч      Е37             , Э50 1210(8) – ГРАФОПОСТРОИТЕЛЬ
        пб      ТВ40            , ВЫЗОВ НЕРЕЗИДЕНТА ТРУБКИ
```

Три разных входа в `гпнити` (коды 1216/1217 отнесены к К-71 в
`rukava.be:3038-3039`):

| Код | Ветка в ТРУБКЕ | Команды перед `пб гпнити` |
|---|---|---|
| 1210 | `.ДА`, `trubka.be:326,335-337` | `СЧ 0; ПБ гпнити` (метка `вхгп2б`) |
| 1216 | `.ДА1`, `trubka.be:351,358-360` | `СЧ E1; ПБ гпнити` (метка `э1216`) |
| 1217 | `.ДА1`, `trubka.be:358-362` | `СЧ 0; ПБ гпнити` (метка `э1217`) |

Коды 1201-1203 и диапазон 1220+ идут через `.ДА2` (`trubka.be:368-380`):
`зп КЛЮЧ; уиа 8(М3); сч ВХ1220; по гпнити; уи М11; пб (М11)`. `ВХ1220`
не является входом в ДУДКУ, это внешняя ячейка ДИСП70
(`trubka.be:797`, `trubka.lst:839` = `00026СА`).

Прямого перехода на ДУДКУ НЕТ. `гпнити` заканчивается `пб ФИЗОБМ`
(`trubka.be:696`), тот же переход повторяется в ветке `нерез`
(`trubka.be:714`), то есть загружается нерезидент с МЛ/МБ. База сохраняется
в `БНСО` (`trubka.be:705`), а ДУДКА стартует `мод БНСО; уиа 0(М16)`
(`dudka.be:54-59`).

Разница двух ветвей после `слиа -8(М3)` (`trubka.be:679`):

- 1210 даёт индекс 0, ветка `пино 0(М3)` (`trubka.be:688`) не срабатывает:
  `или пароль` (`:689`), затем `НОММЛ` и `МАС` (`:692-694`) и `пб ФИЗОБМ`
  (`:696`).
- 1216/1217 дают индексы 6/7, срабатывает `нерез`
  (`trubka.be:687-688,703-714`): `слиа -7(М3)` (`:703`), `зп БНСО` (`:705`),
  `слц п421-ТРУБКА(М7)` (`:707`), `зп трб7яч` (`:708`), таблица трактов
  `заг564`/`гп5` (`:710-717`) и `пб нафиз` (`:714`).

Вывод для стенда: `,*50,1210B` в прослойке `PLOT`
(`verify/native/SHIM.mad:4`, `fortran/verify/PDEV.mad:4`) корректен,
`,*50,1211B` (`SHIM.mad:5`, `PDEV.mad:5`) выдаёт кадр, а коды 1200-1207
кадра не дают: в `dispak/dispak/extra.c:1823-1865` они только логируются
и возвращают `E_SUCCESS`, 1205 печатает `ВК.Г` на терминал (`:1838-1843`),
кадр создаётся только обработчиком 1211 (`:1871-1877`).

### 2.2. Дословный разбор экстракодов 1216/1217

В разделе 2.1 показано, что коды 1216/1217 попадают в `гпнити` через метки
`э1216`/`э1217` и различаются значением, которое `СЧ` оставляет на сумматоре.
Ниже разобраны остальные различия ветвей: арифметика индекса M3, выбор
тракта и нерезидента, смысл `СЧ E1`. Все числа в этом разделе восьмеричные.

#### 2.2.1. Арифметика M3: вычитание 01200₈

Точка входа после экстракода загружает в M3 полный код (`trubka.be:283`,
`СЧИ М3`), и первое вычитание выполняется до входа в `гпнити`:
`СЛИА -'1200'(М3)` (`trubka.lst:69`, строка листинга `10061 03 25 76600`).
Поле `076600₈` в этой строке есть дополнительный код `01200₈`, поэтому на
входе в `гпнити` M3 равен коду экстракода минус 01200₈:

| Экстракод | Код в M3 | После `слиа -8(М3)` (`trubka.be:679`) | После `слиа -7(М3)` (`trubka.be:703`) |
|---|---|---|---|
| 1210 | 010₈ | 0 | не вычисляется |
| 1216 | 016₈ | 6 | 077777₈ (минус 1) |
| 1217 | 017₈ | 7 | 0 |

`СЛИА` это opcode 25 / UTM (`rukava.be:108`). В эмуляторе это
`reg[ui.i_reg] = ADDR(addr + reg[ui.i_reg])` (`dispak/dispak/cu.c:549-551`),
где `ADDR(x)` есть `((ushort)(x) & 077777)` (`dispak/dispak/defs.h:257`),
то есть сложение по модулю 2¹⁵.

Дальше ветви ведут себя по-разному:

| Код | M3 после -8 | `ПИНО 0(М3)` (`trubka.be:688`) | Действие |
|---|---|---|---|
| 1210 | 0 | не срабатывает | `ИЛИ ПАРОЛЬ` (`trubka.be:689`), константа `4070301400000₈` (`trubka.lst:749`), затем `НОММЛ` и `МАС` (`:692-694`), `ПБ ФИЗОБМ` (`:696`) |
| 1216 | 6 | срабатывает, переход в `нерез` | после -7 M3 = -1 (`077777₈`), `ПИО 0(М3)` (`trubka.be:711`) не срабатывает, `ИЛИ КУСГП5` (`400066₈`) плюс `ИЛИ НОММБ1` (`:712-713`) |
| 1217 | 7 | срабатывает, переход в `нерез` | после -7 M3 = 0, `ПИО 0(М3)` срабатывает, метка `ЗАГ564`, `ИЛИ КУС564` (`4056401400000₈`, зона 0564, `trubka.lst:750`) |

Условия переходов подтверждены таблицей `rukava.be:115-116`: `ПИО` это
VZM (34), переход по ИР = 0, `ПИНО` это VIM (35), переход по ИР не равно 0;
в эмуляторе это `cu.c:704-714` и `optab.c:98-99`. Адрес перехода берётся не
из адресного поля самих `ПИНО`/`ПИО` (там 0), а из M20, который заполняет
предыдущая `МОДА`: `мода нерез` (`trubka.lst:676`) записывает адрес
`10371₈`, после чего `пино 0(М3)` (`:677`) переходит туда же;
`мода заг564` (`trubka.lst:699`) записывает `10377₈` для `пио 0(М3)`
(`:700`). MODREG = 020₈ определён в `dispak/dispak/defs.h:62`.

#### 2.2.2. `МОДА 0(М3)` и выбор тракта

В `нерез` команда `мода 0(М3)` (`trubka.lst:695`) копирует M3 в M20.
Следующая `слц п421-ТРУБКА(М7)` (`trubka.lst:696`, код `07 013 0410`)
берёт слово по адресу `010410₈ + M3` (MODREG добавляется к адресу при
выборке, `dispak/dispak/cu.c:226-230`):

- 1216: индекс -1, адрес `010407₈`, там слово `121 + 24·N` (`trubka.be:737`);
- 1217: индекс 0, адрес `010410₈`, там `421₈` (`trubka.be:738`, символ
  `П421`, `trubka.lst:843`).

Результат сохраняется в `ТРБ7ЯЧ` (`trubka.be:708`). Оговорка: «таблица
трактов 0..7» из комментария `trubka.be:700` не доказана, в исходнике видны
только два указанных слова. `ТРБ7ЯЧ` вычисляется, но не используется:
`МОД ТРБ7ЯЧ` (`trubka.be:718`) недостижима, так как на `trubka.be:717`
стоит безусловный `ПБ ПРОВЕР`, а комментарий `trubka.be:721` прямо говорит
«Нет передачи упр. на участок далее».

#### 2.2.3. `СЧ E1` против `СЧ 0`: режим ТБУФ, а не ключ

`СЧ E1` и `СЧ 0` перед `ПБ гпнити` задают не ключ подфункции и не режим
«вкл/выкл» оборудования, а параметр запроса `ТБУФ` на сумматоре.
`E1 = п'000001'` (`siprog.be:59`, символ в таблице `trubka.lst:843`). По
`Dispak-description.md:750-752` параметры ПВ находятся на сумматоре:
`СМ = 0` это запрос листа (`:755`), `СМ = 1` (код 1 в 1-м разряде) это
запрос абзаца для секторных нерезидентов со шкалой `ШКСВМ` (`:765-768`).
`СЛИА` меняет только индексный регистр и не трогает сумматор
(`Besm6_Instruction_Set.md:1129-1138`, раздел 025 UTM, `ω mode: Kept`).
Номер схемы НИТИ передаётся отдельно в M3, а проверка ключа идёт в
диспетчере `НТЖ СОБР`, сравнение с паролем `71717₈` (`trubka.be:288`).
Гипотезы про «вкл/выкл» подтверждения не получили.

#### 2.2.4. Нерезиденты 1216 и 1217

- 1216: `ИЛИ КУСГП5` (`400066₈`, `trubka.be:740`) плюс `ИЛИ НОММБ1`,
  чтение с МБ. Модуля ГП5 в дереве `.be` нет
  (`simh/BESM6/doc/ГП.md:479`), отождествление этого кода с ДУДКОЙ не
  доказано.
- 1217: `ИЛИ КУС564` (`4056401400000₈`, `trubka.be:742`), зона 0564. По
  `rukava.be:2721-2722` это «ПУСТО, ПЛАН, ПУСТО (Д. Б. НЕРЕЗИДЕНТ НОМБОБА),
  ПУСТО», то есть не ГП3 (ГП3 значится в зоне 0565, `rukava.be:2723`).
- `КУСГП3 400022₈` (`trubka.be:736`) встречается только в участке
  `ГПНЕИС` (`trubka.be:722-730`), который помечен как неиспользуемый
  (`:731`). Сам ГП3 реален (`gp3.be:1`, `modloc.txt:35` =
  `гп3 0101 01`), но этими кодами он не грузится.

Обе ветви сохраняют базу в `БНСО` (`trubka.be:705`), а ДУДКА стартует
`мод БНСО; уиа 0(М16)` (`dudka.be:54-59`). Гипотеза: коды 1216 и 1217
грузят один и тот же драйвер из разных источников (ГП5 на МБ и зона 0564),
прямых доказательств этому нет.

### 2.5. Линия 18-го разряда ГРП идёт через `ВНУПР`

Прежнее описание маршрутизировало 18Р через внешний обработчик `ОБВНПР`.
Это ошибка. `disp70.be:222-225` задаёт два разных входа: `500₈` ведёт в
`START` и далее в `ВНУПР` (внутренние прерывания), `501₈` ведёт в `внешпр`
и `ОБВНПР` (внешние разряды 48-25). ДУДКА разрешает именно внутренний
разряд 18 командой `сч E18; пв ТВ67(М15)` (`dudka.be:163-165`), поэтому
18Р обрабатывается в `ВНУПР` (`disp70.be:978-1008`), а не в `ОБВНПР`.

`ВНУПР` сохраняет РК, И17, РМР, И16, И15 и И20 (`disp70.be:982-993`),
читает ГРП через `рег '237'` (`:994-995`), выделяет внутренние разряды
`и ПОДПРГ` (`:996-999`), гасит их через `сч ГАШРП1; уи; рег '37'`
(`:1000-1002`), затем `нед; уи М16; пб обвнп1-1(М16)` (`:1006-1008`).
Повторное чтение ГРП, `МГРП`, `каска` и гашение выбранного разряда через
`сч E48-1(М16); нтж ЕДК10Р` находятся во внешнем пути
(`disp70.be:1431-1451`) и к 18Р отношения не имеют.

Формула вектора: `M16 = 49 - r`, адрес равен `обвнп1 + (48 - r)`.
База таблицы `03765₈` (`disp70.lst:1535`), вектор 18Р `04023₈`
(`disp70.lst:1610`), разница `36₈`, то есть 30 в десятичной записи.
Для r = 18 получается `M16 = 31` и смещение `+30`. Поэтому комментарий
`dudka.be:121` про «31-й разряд» ошибочен: 31 это индекс M16, а не номер
разряда ГРП.

Ещё одна коррекция: в обработчике `ВХОД` (`dudka.be:249-294`) в `РЕГ '34'`
идут **шесть** записей (`:253-264`), а не пять, как писалось раньше.
Первая запись это нуль (`:253-254`), затем `D10167`, нуль, `е28е25`,
нуль, `D10171`. Формула, ветви `G10147/G10150/G10152`, аварии и возврат
разобраны отдельно в `GRP18-INTERRUPT-FLOW.md`.

### 7.2. B3, мостик от Фортрана к экстракоду

Фортран не может напрямую выдавать экстракоды, поэтому добавлен
`fortran/verify/PDEV.mad`. После сквозной передачи координат он стал
указателем на кадр, а не генератором мусора:

```
 PDEV: ,NAME,PDEV
       1, VTM,
       ,ATI,11
       ,STX,
       ,ITA,11
       ,*50,1210B
       ,ITA,11
       ,*50,1211B
       13, UJ,
       ,END,
```

Контракт кадра (совместно с `dispak/dispak/extra.c`, `du_decode_stream`):
слово 0 = X в шагах 0.1 мм (восьмеричное целое), слово 1 = Y, слово 2 =
состояние пера (0 поднято, 1 опущено), слова 3..63 = 0.

Соглашение вызова FORTRAN -> МАДЛЕН: `PLOT()` берёт точку из
`COMMON /GFAFTR/` (её записывает `MOVE`), преобразует в `INTEGER` и
заполняет `COMMON /PDEVXY/` (64 слова), затем вызывает
`CALL PDEV(FRAME(1))`. Для одного аргумента его адрес приходит в
сумматоре (MADLEN, §46: `besm6.net/book/fortran-1976/03-madlen.md`);
`ATI,11` сохраняет его в R11, `STX` выталкивает сохранённый сумматор и
восстанавливает магазин, `ITA,11` загружает адрес обратно перед каждым
ЭК. `ЭК 01211` читает адрес кадра из аккумулятора, а `ЭК 01210` может
аккумулятор испортить, поэтому загрузка повторяется. Фиксированного
адреса COMMON больше нет: раньше он был `0o3147` для деки C1-line
(из `*PDEVXY* C 03147`), теперь кросс-ссылка даёт `0o3150`, у дек с
большим числом констант `0o3155`/`0o3160`, и все они рисуют.

Оговорка: MADLEN не разрешает внешние символы FOREX по имени (та же
причина, по которой в re-forex `docs/plan-f77-full/33-arfa-perso-lib.md`,
§1 п.4, захардкожен `/FILMAP*`), а FOREX не поддерживает вставки
ассемблерного кода в FORTRAN-единицу. PDEV поэтому остаётся отдельным
МАДЛЕН-модулем в PERSO-зонах `0o2750` и `0o2760`; связь с FORTRAN идёт
через аргумент, а не через символ COMMON. Ранее `BUF: ,BSS,64` не
использовался: `*50` в записи ЭК — это код экстракода 050, а не адрес
буфера.

Поскольку FORTRAN хранит `INTEGER` с тегом типа в старших 24 битах
(`0xd00000...`), декодер dispak в режиме `coords` берёт младшие 24 бита.
`BESM6_NITI_DECODE=proven|dubna|raw` сохраняет прежний сырой путь
6 байт/слово для A/B-сравнения.

`PDEV` собран в PERSO-библиотеку зоны `0o2760` и продублирован в последней
зоне порта `0o2750`.
В `fortran/PLOTSTUB.FTN` процедура `PLOT()` после инкремента `NPLOT`
вызывает `CALL PDEV(FRAME(1))`. Цепочка замкнулась:

```
Fortran MOVE() -> /GFAFTR/ -> PLOTSTUB (NPLOT++) -> /PDEVXY/
              -> PDEV -> ЭК 1210/1211 -> dispak extra.c -> plot.dat
              -> coords decoder -> benson.out -> plotter.cpp -> benson.svg
```

PERSO-библиотеки порта занимают **свободные** зоны, начиная с `0o2410`:
`0o2410..0o2470`, `0o2510..0o2550`, `0o2630..0o2670`, `0o2720..0o2750`
(21 группа по 12 исходных файлов), плюс выделенная зона PDEV `0o2760`.
Так как каталог PERSO вмещает не более 31 имени, а текущие группы
уже дают до 31 имени, уплотнение сверх 12 файлов невозможно без переполнения
каталога; «уплотнение» здесь означает отсутствие пропусков между занятыми
зонами. Исходный образ: `fortran/verify/2348-niti.img`, скрипт пересборки:
`fortran/verify/build-niti-disk.sh` (он начинает с нетронутого
`/usr/local/share/besm6/2348`).

Рабочая копия, которую используют все раннеры по умолчанию, лежит в
`~/.besm6/2348` (вместе с дисками `2048`, `2053`, `2099`, `2148` в том же
каталоге, `BESM6_PATH=$HOME/.besm6`). Это побайтовая копия
`fortran/verify/2348-niti.img`, SHA `29363feb10be…`. Системные зоны
`0o2400` (FOREX), `0o2500`/`0o2560` (GOSTLIB), `0o2570..0o2637` (рантайм
Паскаля) и `0o2700..0o2710` (Глиссада-6) в ней восстановлены из исходного
тома и не перезаписаны.

⚠ **Зона `0o2700` не свободна.** По `re-dispak/rukava.be:24,3214-3236` это
тренажёр «Глиссада-6» на томе 2348: 8 зон по 1024 слова, каталог
`GLDIAL, PROGRAM, FUELTV, FUELGT, …` плюс рантайм Паскаля в зонах
`0o2570..0o2637`. Попытка собрать туда `verify/native/shim.b6` затирает
Глиссаду, поэтому в рабочей копии зона `0o2700` оставлена нетронутой.
МАДЛЕН-прослойку для нативных тестов собирают на **отдельной** копии диска
в `/var/tmp`, как описано в `verify/native/README.md`. Деки порта зону
`0o2700` не подключают: их `PLOT` берётся из `0o2750`.

Воссоздание рабочей копии (однократно):

```

cp /home/azizz/Yandex.Disk/dispak/build/dispak/{2048,2053,2099} ~/.besm6/
cp /usr/local/share/besm6/2148 ~/.besm6/
cp fortran/verify/2348-niti.img ~/.besm6/2348
```

Все раннеры используют `~/.besm6/2348` без явного `NITI_2348`.

⚠ В `NITI-EMULATION-PLAN.md:15,84,93` указывается строка `extra.c:1700-1727`
как обработчик 1211; в текущем HEAD `87f317b` фактический обработчик
находится в `extra.c:2722-2728`, а запись в `extra.c:259-281`. Также
обработчик 1211 не может вызывать `niti_frame()` из `ФИЗОБМ`:

Корневая причина прежних отказов C2/C3: дублирующие `ENTRY`-заглушки в

настоящий `ARCIA.FTN` (`0o2410`); так же `SYMBOL` из `XLGAX.FTN` и `NUMBER`
из `INSDEK.FTN`. После удаления псевдонимов и установки координат в
`/GFAFTR/` перед `CALL PLOT()` все тесты прошли.

### 8.3. Родная библиотека 22 с прослойкой точек входа

Чтобы прогнать **родной** DMS-код библиотеки 22, не хватало точек входа
вторичного каталога: `PLOT`, `MOVE`, `RDB`, `ENDPG`, `PAGE`. Они собраны в
МАДЛЕН-прослойке `verify/native/SHIM.mad` и записаны в PERSO зону `0o2700`.
`PLOT` выдаёт ЭК 1210 и 1211, остальные точки возвращаются через `13,UJ,`.

Результат (`verify/native/README.md`, проверено дважды):

```
NITI: scheme 1210 selected
NITI: summary schemes=1 frames=1 words=64 active=1 scheme=1210
 КОНЕЦ ЗАДАЧИ
```

`plot.dat`: 1600 байт, 64 строки, SHA
`15450e0b433bfbc2c2cac11d2528e7a9626f444a0d60b2290c6b325ddff25b2d`.
Нативный вызов `MOVE1(N,X,Y)` + `ARCIA(0.0)` отработал без `ОТСУТСТВУЕТ`
и `E_UNIMP`. Для сравнения, наш Фортран-порт в тесте C1-line даёт 2 кадра,
3200 байт, SHA `7b362ec4efd7...`. Разница объясняется разными программами
и координатами, а не несовместимостью протокола.

Отдельно добавлена имитация ЭК 1200-1207 в `dispak/extra.c` (коммит
`a4c177b`): они возвращают `E_SUCCESS` и пишут диагностику, снимая путь
`E_UNIMP`. ЭК 1205 по коду `trubka.be:490-507` не выдаёт кадр, а печатает
`ВК.Г` на терминал, поэтому `plot.dat` по-прежнему создаётся только через 1211.
