# Критерии честного сравнения: родная библиотека 22 vs Фортран-порт

Этот файл описывает, что **обязано** совпадать у родной деки (library 22) и у
портовой деки (C1-C5), а что **нельзя** требовать совпадать. Раннер
`./run.sh` реализует именно эти критерии; всё остальное он только печатает.

Обе стороны прогоняются через **один и тот же** `dispak` с окружением:

```
BESM6_DUDKA_PLOT=benson BESM6_DUDKA_TEST=1 BESM6_DUBNA_PLOT_KEEP=1
```

Родная дека использует `*library:22` + SHIM в PERSO `0o2700`; портовая -
PERSO `0o2400..0o2650`, `/PDEVXY/` и coords-декодер. Разница в захвате кадра
допустима, сравнение идёт по выходным артефактам.

## 1. Обязательно должно совпадать

### 1.1 Формат кадра `plot.dat`

Обе стороны пишут кадр через одну функцию `niti_plot_write()` в
`dispak/dispak/extra.c`: одно 48-разрядное слово = 8 восьмеричных 6-битных
групп, 8 чисел на строку, 64 строки на кадр, 25 байт на строку.

Инварианты (проверяются отдельно для каждой стороны, затем сравниваются):

- файл существует, непуст, число строк кратно 64;
- каждая строка имеет вид `NN NN NN NN NN NN NN NN` (цифры `0..7`);
- нет кадров, целиком состоящих из нулей;
- `frames = wc -l / 64` - целое число.

Это совпадение **формата**, а не содержимого. Требовать побайтового равного
`plot.dat` здесь нельзя: разные программы выдают разные точки.

### 1.2 Алфавит команд БЕНСОНА

`benson.out` обеих сторон обязан содержать только коды (с ведущим нулём или
без) `06501`, `06502`, `06504`, `06511`, `06512`, `06514` и пометку
`[аналог NASA, БЕНСОН-501]` в каждой строке. Множество встретившихся кодов
(отсортированное, уникальное) должно совпасть у обеих сторон для сравнимых
заданий: обе проходят через один и тот же `du_decode_stream()` /
`du_decode_benson_step()`.

**Не обязаны** совпадать: порядок команд, их число, координаты `X=/Y=`,
последовательность шагов. Родная дека с неинициализированным буфером
формально тоже даёт тот же алфавит - и именно поэтому одного алфавита
недостаточно, нужна ещё готовность родной стороны (раздел 3).

### 1.3 Детерминированность

Каждая дека прогоняется дважды. Для обеих сторон обязаны совпасть полные
SHA256 всех трёх артефактов:

```
plot.dat    benson.out    benson.svg
```

Несовпадение между r1 и r2 - отдельная находка, а не «почти совпадение».

### 1.4 Структура SVG

- `benson.svg` начинается с `<?xml`;
- есть хотя бы один `<path>`;
- атрибуты `width`/`height` присутствуют.

Значения `width`/`height` и содержимое `d="..."` сравнить **нельзя**:
они следуют из координат конкретной деки.

### 1.5 Успешность прогона

В логе обеих сторон: `КОНЕЦ ЗАДАЧИ`, `NITI: summary ...`, отсутствие
`ОШ`/`ОТСУТСТВУЕТ`/`ERR nnnn` (в обеих транслитерациях, латиница тоже
проверяется). Для обновлённой родной деки дополнительно не должно быть
`ВЫВОД ЗАПРЕЩЕН`.

## 2. Что может и должно отличаться

| Параметр | Родная библиотека 22 | Наш порт |
|---|---|---|
| Источник координат | `RDB` -> `*GFATRN*`/`*GFBLAN*`, общие блоки ГРАФОР | константы в Fortran, COMMON `/GFAFTR/`, `/PDEVXY/` |
| Число кадров на задание | `MOVE1.mad:206` вызывает `PLOT` один раз | C1 явно вызывает `PLOT` дважды |
| Порядок шагов X/Y | определяется алгоритмом `MOVE1` + масштабированием | decoder выдаёт перо, затем все X, затем все Y |
| SHA256 plot.dat | свой | свой |
| Размер benson.out / число команд | свой | свой |
| Размер и геометрия SVG | свой | свой |
| Статус вывода | пока `ВЫВОД ЗАПРЕЩЕН` (ошибка 25 ДИСПАК) | выход через собственный мостик `PDEV` |

Поэтому раннер **не** имеет права требовать: равные SHA, равное число
кадров, равные координаты, одинаковую длину `benson.out`, одинаковый
размер SVG. Он печатает их как справочные величины.

## 3. Готовность родной стороны

Раннер не объявляет сравнение состоявшимся, пока выполняется хотя бы одно из:

- нет родной деки для пары (сейчас так для C2-C5);
- используется legacy `verify/native/native-final.b6` + SHIM из `BSS,64`
  без записи координат в буфер кадра;
- в логе родной деки есть `ВЫВОД ЗАПРЕЩЕН`;
- `plot.dat` родной деки имеет SHA
  `15450e0b433bfbc2c2cac11d2528e7a9626f444a0d60b2290c6b325ddff25b2d`
  (эталон неинициализированного BSS);
- кадр(ы) целиком из нулей;
- родная сторона недетерминирована между r1 и r2.

В этом случае verdict - `НЕ ГОТОВО`, а не `PASS` и не `СОВМЕСТИМО`.
Артефакты субагентов A/B ищутся в `verify/native-decks/` (и перекрывают
legacy-деку); деки и SHIM, найденные там, считаются обновлёнными. Явный
override: `NATIVE_SHIM_B6=/path/to/shim.b6`.

## 4. Почему нельзя требовать совпадения с эталонами Дубны

- Дубнинские «golden» `plot.dat` получены по другому тракту: 6 байт на
  слово, proved CalComp-подобная раскладка битов (`BESM6_NITI_DECODE=proven`,
  `BESM6_DUDKA_PLOT` выключен). Это `[аналог CalComp]`, а не протокол НИТИ.
- Наш бэкенд в режиме `benson` использует coords-декодер
  (слово 0 = X, слово 1 = Y, слово 2 = перо, шаг 0.1 мм) и коды
  `065xx` как `[аналог NASA, БЕНСОН-501]`.
- NASA TM-76182 описывает сопряжение `BENSON-FRANCE 501` с
  `Электроникой-1001`; это OSINT-подтверждение физической модели (5 шин,
  шаг 0.1 мм, шесть 12-битных команд), а не спецификация интерфейса
  БЭСМ-6/НИТИ. Прямое отождествление NASA-кодов с протоколом НИТИ
  опровергнуто, см. `docs/BENSON-PROTOCOL.md` и
  `docs/DUBNA-PLOTTER-BRIDGE.md`.
- Как следствие, эталоном для честного A/B служит **один и тот же dispak
  на одной и той же сборке**, а не числа из Дубны и не из NASA-отчёта.

Ссылки: `docs/reference/NASA-TM-76182.pdf`, `docs/reference/README.md`,
`docs/BENSON-COMMAND-FORMAT.md`, `docs/BENSON-PROTOCOL.md`,
`docs/DUBNA-PLOTTER-BRIDGE.md`, `docs/NATIVE-RUN-ALGORITHM.md`.

## 5. Коды возврата раннера

| Код | Значение |
|---:|---|
| 0 | все пары `СОВМЕСТИМО` |
| 1 | есть `НЕ ГОТОВО` или `РАСХОЖДЕНИЕ` (норма для текущего состояния) |
| 2 | нет обязательного файла/деки |
| 3 | в `dispak` нет маркера `BESM6_DUDKA_PLOT` |
