# Ожидаемое содержимое benson.out и benson.svg

Статус: контракт и результаты первого честного прогона. На момент
подготовки бэкенда в бинарнике dispak не было маркера `BESM6_DUDKA_PLOT`,
и `run.sh` останавливался с FAIL, не выдумывая результаты. После сборки
бэкенд проверен: `run.sh` даёт `1 PASS`, SHA `plot.dat` остался прежним.
Числа ниже помечены как наблюдение текущей сборки, а не как доказательство
исторического протокола.

## 1. Формат benson.out

`benson.out` это текстовый поток команд БЕНСОНа, одна команда на строку.
Число в начале строки это восьмеричный код NASA TM-76182, таблица 2
(стр. 6-7 PDF). Коды сверены по изображению PDF, а не по искажённому
текстовому распознаванию `docs/reference/NASA-TM-76182.txt`.

| Команда | Шина | Код (восьм.) | Начало строки |
|---|---|---:|---|
| `+X` | `+X` | `6502` | `6502 +X` |
| `-X` | `-X` | `6514` | `6514 -X` |
| `+Y` | `+Y` | `6501` | `6501 +Y` |
| `-Y` | `-Y` | `6504` | `6504 -Y` |
| `UP`, перо вверх | `Pen Control` | `6511` | `6511 UP` |
| `DOWN`, перо вниз | `Pen Control` | `6512` | `6512 DOWN` |

Формат строки, наблюдаемый после честного прогона деки C1-line:

```
6512 DOWN X=00000 Y=00000 [аналог NASA, БЕНСОН-501]
6502 +X X=00001 Y=00000 [аналог NASA, БЕНСОН-501]
6502 +X X=00001 Y=00000 [аналог NASA, БЕНСОН-501]
6512 DOWN X=00001 Y=00000 [аналог NASA, БЕНСОН-501]
6501 +Y X=00001 Y=00001 [аналог NASA, БЕНСОН-501]
```

То есть код, мнемоника, координаты пера в шагах 0.1 мм и полная пометка
аналога в каждой строке. Первой в текущей сборке идёт команда `6512 DOWN`,
а не `UP`: это наблюдение кода декодирования, а не требование к протоколу.
В восьмеричной нотации код иногда пишут с ведущим нулём (`06511`,
`06502`), раннер допускает обе формы.

Наблюдаемый набор кодов для C1-line: `6501`, `6502`, `6504`, `6511`,
`6512`, `6514`, то есть все шесть команд таблицы 2 NASA. Точное число
строк, размер файла и SHA `benson.out`/`benson.svg` намеренно не
фиксируются: владелец `dispak/` продолжает изменять отображение кадра
в команды. Раннер сравнивает эти SHA только между двумя прогонами одной
сборки. Единственный фиксированный SHA это SHA `plot.dat`, и его менять
нельзя.

Раннер обязательно требует наличия кодов `06511`/`6511` и `06502`/`6502`.
Остальные четыре кода допустимы, но их наличие не требуется. Пометка
`[аналог NASA, БЕНСОН-501]` обязательна в `benson.out`, раннеру достаточно
подстроки `[аналог NASA` в `benson.out` или в логе прогона.

## 2. Почему нельзя сверять с эталонами Дубны

Эталоны `tests/expect_calcomp_output.bin` и `tests/expect_calcomp.svg`
принадлежат другой программе и другому прибору.

1. Разные устройства. NASA TM-76182 описывает `BENSON-FRANCE` 501 с
   пятью шинами `+X/-X/+Y/-Y/Pen Control`, шагом 0.1 мм и кодами
   `6501/6502/6504/6511/6512/6514` для Электроники-1001. CalComp Дубны
   это байтовый поток с битами `01` (`-X`), `02` (`+X`), `04` (перо
   вверх), `010` (перо вниз), `020` (`+Y`), `040` (`-Y`). Совпадение
   названий осей не делает форматы одинаковыми: различаются носитель,
   адресация, единицы измерения и смена страницы.
2. Разные программы. Эталоны Дубны получены из дек
   `examples/grafor/*.dub`, например `calcomp.dub` рисует строку
   `Calcomp` через `CALL PAGE(14.0, 10.0, 'PAGE', 4, 0)`,
   `CALL LIMITS(0.0, 14.0, 0.0, 10.0)` и `CALL SYMBOL(...)`. Наша дека
   рисует прямую линию через PERSO 4.12 на диске 2348. Разные координаты
   дают разные потоки шагов. Аналогичный случай описан в
   `docs/NITI-CALL-DETAILED.md:582`: разница между нативным вызовом и
   C1-line объясняется разными программами, а не несовместимостью.
3. Разный уровень. `plot.dat` это 64 слова на кадр, восемь шестибитных
   групп на строку. `benson.out` это список восьмеричных команд. Эталон
   Дубны проверяет, что `plotter.cpp` принял байты от ЭК `*57`. Этот тест
   проверяет другое: что новый слой доставил в тот же проверенный
   приёмник команды, полученные из кадра `plot.dat`, и сделал это
   воспроизводимо, не изменив сам `plot.dat`.
4. Слово `proven` относится к коду `plotter.cpp`, который проверен
   эталонами Дубны, а не к происхождению команды NASA и не к протоколу
   НИТИ. Любая успешная сверка с `expect_calcomp*` была бы ложным
   доказательством советского протокола.

По этой причине раннер не сравнивает `benson.out` ни с одним эталоном
Дубны. Единственный фиксированный эталон здесь это SHA `plot.dat` деки
C1-line: `181ed477d5a97392d092978cccefa9b56f7434d56d1f373952f8325e6dd585ea`.

## 3. Как проверять benson.svg

Файл должен создаваться тем же кодом рендера `plotter.cpp`, который уже
проверен в Дубне, через C ABI мост. Новый агент не копирует алгоритм SVG,
а переиспользует существующий приёмник. Ожидаемые признаки SVG:

Заголовок, наблюдаемый в рабочей сборке:

```
<?xml version="1.0" encoding="utf-8" ?>
<svg xmlns="http://www.w3.org/2000/svg" xmlns:ev="http://www.w3.org/2001/xml-events" xmlns:xlink="http://www.w3.org/1999/xlink" baseProfile="full" version="1.1" width="41" height="48" viewBox="0 0 41 48">
<g fill="none" stroke="black" stroke-linecap="round" stroke-width="1">
<path d="M 1 2 1 0 0 0"/>
...
</g>
</svg>
```

Инварианты по коду `plotter.cpp`:

- `width`/`height` равны `maxx + 1 - minx` и `maxy + 1 - miny`,
  координаты нормализуются через `x - minx` и `maxy - y` (в SVG ось Y
  направлена сверху вниз);
- `<path>` появляется только если накоплено не менее двух точек, поэтому
  пустой поток или одиночная точка не дают `<path>`;
- коллинеарные промежуточные точки отбрасываются, поэтому вершин в
  `<path>` меньше, чем шагов в `benson.out`;
- в генераторе нет временных меток, случайных чисел и номеров процесса,
  значит при байтово одинаковом `benson.out` файл `benson.svg`
  детерминирован;
- при включённой нумерации страниц имя файла может стать `benson1.svg`,
  `benson2.svg` и так далее (`append_suffix`). Раннер ожидает именно
  `benson.svg`: в C1-line смена страницы не требует нескольких файлов.

Ручная проверка с сохранённым рабочим каталогом:

```
KEEP_WORK=1 ./verify/benson-commands/run.sh
sha256sum $WORK/run/C1-line-r1/benson.svg $WORK/run/C1-line-r2/benson.svg
cmp $WORK/run/C1-line-r1/benson.out $WORK/run/C1-line-r2/benson.out
```

Если доступен `xmllint`, дополнительно проверить корректность разметки:

```
xmllint --noout $WORK/run/C1-line-r1/benson.svg
```

Что важно:

- сравнение делается внутри одной сборки dispak, между разными сборками
  детерминированность не гарантируется;
- стабильность `benson.out` не отменяет проверку `plot.dat`, оба файла
  должны быть стабильными, и SHA `plot.dat` должен остаться прежним;
- если в SVG появится дата или порядковый номер, тест должен упасть:
  значит используется генератор, отличный от `plotter.cpp`.

## 4. Что проверяет раннер, а что нет

| Проверка | Есть в run.sh | Комментарий |
|---|---|---|
| Маркер `BESM6_DUDKA_PLOT` в бинарнике | да | без него честный FAIL, exit 3 |
| Строка `NITI: summary ...` | да | подтверждает, что дека реально отработала |
| Прежний SHA `plot.dat` | да | полное значение для C1-line |
| Наличие и непустота `benson.out`, `benson.svg` | да | |
| Коды `06511`/`6511` и `06502`/`6502` в `benson.out` | да | регулярное выражение по строке |
| Пометка `[аналог NASA` | да | в `benson.out` или в логе |
| SHA между r1 и r2 | да | для трёх файлов сразу |
| Набор остальных кодов и число строк | нет | наблюдаемые значения записаны в разделе 1 |
| XML-валидация SVG | нет | делается вручную, см. раздел 3 |
| Совпадение с эталонами Дубны | нет | неприменимо, см. раздел 2 |
| Запуск `ctest` | нет | его запускает lead |
