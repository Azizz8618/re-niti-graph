# Попытка получить осмысленный кадр из родной библиотеки 22

Итог: **BLOCKED**. Нативный код библиотеки 22 выполняется, но превратить
координаты `*GFAFTR*` в шаги 0.1 мм внутри МАДЛЕН-прослойки надёжно не удалось.
Ниже только проверенные факты, без выдуманных результатов.

## 1. Адреса COMMON из кросс-ссылки

Дека `native-final.b6` с `*full list` и `*system load list`
(`/var/tmp/native-work/nat-full.out`) даёт:

```
        MOVE1      01056
        STOP*      01616
        *GFBFTR* C 01637
        *GFAFTR* C 01641
        *GFATRN* C 01643
        *GFBLAN* C 01652
        INT        02277
        PLOT       02305
```

Если в Fortran-деке объявить `COMMON /GFAFTR/`, линкер перераспределяет
адрес:например, для деки с двумя `CALL MOVE1` получилось `*GFAFTR* C 01061`,
`PLOT 02067`; для деки с одним вызовом `*GFAFTR* C 01055`, `PLOT 02063`.
Адрес буфера кадра в МАДЛЕН тоже зависит от раскладки, поэтому
захардкоженный `BUFPL` из PDEV-стиля не является стабильным: подбор адреса
в диапазоне `0o2000..0o2400` не дал воспроизводимого кадра.

## 2. Формат данных

Проверено дампом памяти через диагностическую прослойку:

* `*GFBFTR*` по `0o1637` содержит `64 00 00 00 00 00 00 02`
  (FORTRAN-целое 2) и `42 12 00 00 00 00 00 00` (BESM REAL 10.0).
* `*GFAFTR*` по `0o1641` в момент вызова `PLOT` равен нулю.
* BESM REAL 10.0 = `42 12 00 00 00 00 00 00`,
  BESM REAL 110.0 = `43 55 60 00 00 00 00 00`.
  Преобразование через `get_real()` из `dispak/dispak/arith.c:17`
  подтверждено локальным расчётом.
* FORTRAN INTEGER в COMMON имеет тег `64 00 00 00 ...` в старших 24 битах;
  декодер `du_coord_value()` (`extra.c:693`) берёт младшие 24 бита.
  Эталонные три слова кадра C1-line:
  `64 00 00 00 00 00 00 12`, `64 00 00 00 00 00 00 12`,
  `64 00 00 00 00 00 00 01`; вторая точка `... 01 56`.

## 3. Почему `*GFAFTR*` пуст

`madlen/MOVE1.mad:206-210` вызывает `13,VJM,PLOT`, и **только после этого**
пишет X/Y в `*GFAFTR*`/`GAK/4`. Текущая заглушка `RDB` в `SHIM.mad`
возвращается через `13,UJ,` и не выдаёт аргументы, поэтому масштабированные
значения, которые `MOVE1` пишет в COMMON, мусорные. Для первого кадра
`*GFAFTR*` ещё не заполнен. Это объясняет нули в исходном `plot.dat`
и несовпадение с портом.

## 4. Что пробовалось и не сработало надёжно

1. Прямое чтение `*GFAFTR*`/`*GFBFTR*` абсолютными адресами в МАДЛЕН
   (`,XTA,1641B` и т.п.) и копирование в `BUFPL`: адреса из кросс-ссылки
   верны, но результат зависит от раскладки дека/библиотеки; стабильного
   кадра, совпадающего с портом, получить не удалось.
2. Вызов библиотечной процедуры `INT` из прослойки
   (`13,VJM,INT` с адресом аргумента в аккумуляторе): в одном прогоне
   первый кадр действительно получился
   `64 ...12 / 64 ...12 / 64 ...01` (совпадает с портом), но затем
   `PLOT` стал вызываться повторно (до 4·10⁵ кадров), то есть вызов `INT`
   разрушает магазин/состояние вызова. Воспроизвести стабильно не удалось,
   поэтому этот вариант не принят.
3. Попытка писать кадр прямо в `COMMON /PDEVXY/` (как в порту):
   прошивка адреса из кросс-ссылки (`*PDEVXY* C 01425`, затем `01077`)
   не привела к корректному кадру: `ЭК 01211` читает другое слово.
4. Запись целых чисел в `COMMON /GFAFTR/` из Fortran (`INTEGER GFAF(2)`)
   и копирование сырых слов: в момент `PLOT` по адресу из кросс-ссылки
   лежат нули.

Дополнительно учтено сообщение субагента B: заглушки `MOVE/RDB/...`
должны выталкивать аргументы и восстанавливать R15; иначе многосегментные
фигуры (`BOX`) зацикливаются. В текущей работе это не исправлено, так как
изменение заглушек сдвигает адреса и ломает и без того хрупкую привязку
к абсолютным адресам.

## 5. Минимальные изменения в dispak, которые решили бы задачу

Редактировать `dispak/` в этой задаче запрещено, поэтому ничего не внесено.
Достаточно одного нового режима декодера в `dispak/dispak/extra.c`:

* добавить режим `BESM6_NITI_DECODE=coords-real`;
* в `du_decode_stream_coords()` (или в `du_coord_value()`) для слов 0 и 1
  вызывать уже существующий `get_real()` из `arith.c` (он уже линкуется),
  округлять результат до целого и проверять диапазон `0..limit_x/y`;
* слово 2 (перо) оставить как есть, слова 3..63 не трогать.

Тогда `SHIM.mad` может просто копировать два сырых слова `*GFAFTR*` в
`BUFPL` (REAL 10.0 и REAL 110.0), выставлять перо=1 и выдавать
`ЭК 1210/1211`. Преобразование REAL в шаги делается в dispak, где уже есть
проверенная арифметика BESM, а не в МАДЛЕН. Дополнительно следует
Правильная заглушка `RDB` с выталкиванием аргументов и восстановлением R15
(см. `docs/GRAFOR-NATIVE-SIGNATURES.md`), иначе `MOVE1` формирует
координаты из мусора.

## 6. Состояние файлов

`SHIM.mad`, `shim.b6`, `native-final.b6`, `plot.dat` и образ

## 7. Проверка гипотезы «координаты лежат в аргументах PLOT»

Проверка выполнена в `/var/tmp/native-hyp/` (временная копия SHIM, рабочие
файлы задачи не изменялись). По соглашению
`besm6-new/besm6.net/book/fortran-1976/03-madlen.md:689-721`, `PLOT` вызван
`MOVE1` как SUBROUTINE с тремя параметрами: в магазине лежат адреса
`*0306B`, `*0305B`, `*0312B`. Рабочая последовательность извлечения
(проверена ассемблером и прогоном):

```
 PLOT: ,NAME,PLOT
 ,STI,14              . C: адрес-param3, магазин сдвинут
 BUFPL: ,BSS,64
 ,STI,12              . B: адрес-param2
 ,ATI,11              . A: адрес-param1 (магазин не трогает)
 ,STX,BUFPL+63        . третий pop, acc=адрес-param1 пишем в последнее слово
 11,XTA,              . читаем память по адресу param1
 ,ATX,BUFPL
 12,XTA,              . память по адресу param2
 ,ATX,BUFPL+1
 ,XTA,=:00000000 00000001
 ,ATX,BUFPL+2
 . слова 3..63 обнуляются, затем XTA адреса BUFPL и ЭК 1210/1211
```

Результат прогона нативной деки `native-final.b6` с `MOVE1(N,X,Y)`:

* извлечённые адреса: `R14 = 0o1370` (param3), `R12 = 0o1363` (param2),
  `R11 = 0o1364` (param1). Это ровно `*0305B` и `*0306B` модуля `MOVE1`,
  загруженного по `0o1056`, то есть механизм извлечения работает верно;
* по адресу `0o1364` (param1, `*0306B`) лежит
  `64 00 00 00 00 00 00 00`, по `0o1363` (param2, `*0305B`) тоже
  `64 00 00 00 00 00 00 00`: это FORTRAN-целое 0, а не REAL 10.0/110.0;
* по адресу `0o1370` (param3, `*0312B`) лежит `64 … 02`;
* кадр `plot.dat`: words 0/1 = `64 … 00`, word 2 = `64 … 01`, остальные
  нули. Ожидаемых `42 12 …` и `43 55 60 …` нет.

Вывод: **гипотеза опровергнута в части содержимого**. Аргументы `PLOT`
доступны и извлекаются корректно, но ячейки `*0305B`/`*0306B` к моменту
вызова содержат INTEGER 0 (результат `INT` над нулевым значением), а не
REAL-координаты. Причина та же: заглушка `RDB` в SHIM не возвращает
значения из массивов `X/Y`, поэтому `MOVE1` масштабирует нули. Чтение
аргументов само по себе снимает необходимость знать адрес COMMON, но не
решает задачу без исправления `RDB` (и, видимо, без выталкивания
аргументов/восстановления R15 в остальных заглушках).

Общий статус работы остаётся **BLOCKED**; проверка гипотезы **DONE**.

## 8. Фокусированная попытка исправить `RDB`

Выполнена в `/var/tmp/rdb-hyp/` (инструментирование) и `/var/tmp/rdb-work/`
(рабочая попытка). Исходные файлы задачи снова не изменялись.

Инструментированная заглушка `RDB` (FUNCTION с одним параметром, адрес
которого приходит в аккумуляторе через `,ITA,14` перед `13,VJM,RDB`) писала
в отдельный кадр: входной адрес, возвращаемое значение, `R13` и слово по
адресу аргумента. Прогон деки `native-final.b6` с `MOVE1(N,X,Y)`, `N=2`,
`X=(10,110)`, `Y=(10,110)` дал ровно **два** вызова `RDB`:

| Вызов | адрес аргумента | R13 | слово по адресу аргумента |
|---:|---:|---:|---|
| 1 | `0o1564` | `0o1453` | `64 00 00 00 00 00 00 21` (INTEGER 17) |
| 2 | `0o1562` | `0o1455` | `64 00 00 00 00 00 00 01` (INTEGER 1) |

Пять вызовов из исходника `MOVE1.mad` в этом прогоне не выполняются:
реализуется только ветка `*0055B`. Адреса `0o1562/0o1564` лежат в области
данных `MOVE1`, это не массивы `X/Y` пользователя (те были по `0o1026/0o1031`
в первом прогоне без COMMON).

Далее в `/var/tmp/rdb-work/` `RDB` был заменён на счётчикный вариант:
счётчик в `,LOG,` ячейке, индекс через `,ATI,14`, таблица из четырёх
`REAL`-констант в самой заглушке (`10.0, 10.0, 110.0, 110.0`), возврат
`14,XTA,TABLE` и `13,UJ,`. `PLOT` оставался вариантом с извлечением трёх
аргументов (раздел 7). Результаты:

* таблица с «дамповыми» кодировками `4212000000000000` (10.0) и
  `4355600000000000` (110.0): кадр `64 … 24 / 64 … 144 / 64 … 01`,
  то есть 20 и 100, а не 10 и 110;
* таблица с нормализованными кодировками тех же чисел
  (`4164000000000000`): кадр `64 … 44 / 64 … 44 / 64 … 01` (36, 36);
* таблица `5.0/11.0` (`4124000000000000` / `4166000000000000`):
  кадр `64 … 11 / 64 … 11 / 64 … 01` (9, 9).

То есть `MOVE1` действительно вызывает `INT` и получает `INTEGER` с тегом
`64…`, но масштабирование и/или представление REAL критически влияют на
результат. Ни одна из проверенных комбинаций не дала требуемые
`64 … 12` (10) и `64 … 01 56` (110). Прогоны с вызовом `ARCIA` в конце деки
завершались таймаутом (`exit=124`), поэтому дальше результаты не проверялись.

Вывод: за отведённый один заход задачу закрыть не удалось. Нужно решение
пользователя: либо разрешить правку `RDB` в dispak/Fortran-деке с точным
описанием формата аргумента `0o1562/0o1564`, либо принять режим
`coords-real` из раздела 5. Текущие `SHIM.mad`, `shim.b6`,
`native-final.b6`, `plot.dat` и образ остаются прежними, воспроизводимо
рабочими (но с нулевым кадром).
