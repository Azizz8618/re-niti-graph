# Ожидаемые геометрические признаки тестовых рисунков

Набор проверяет, что графопостроительный тракт
`FOREX MOVE -> /GFAFTR/ -> PLOT -> /PDEVXY/ -> PDEV -> ЭК 1210/1211 ->
plot.dat -> coords-декодер -> benson.out -> plotter.cpp -> benson.svg`
остаётся рабочим при изменении только координат.

## Почему менять можно только две константы

`fortran/verify/PDEV.mad:19,21` захардкожил адрес COMMON `/PDEVXY/` = `0o3147`.
Это адрес из кросс-ссылок деки `verify/C1-line.b6` (`*PDEVXY* C 03147`).

FOREX 4.12 при компиляции дедуплицирует константы. Пул констант в протоколе
(`KOHCTAHT ...`) имеет размер `4 + 2*N` восьмеричных слов, где `N` число
различных значений среди четырёх координат двух вызовов `MOVE`:

| Число различных значений N | `KOHCTAHT` | `*PDEVXY*` | Рисунок |
|---:|---|---|---|
| 1 | `00006` | `0o3145` | пустой (адрес сдвинут) |
| 2 | `00010` | `0o3147` | норма, все деки набора |
| 3 | `00012` | `0o3151` | пустой |
| 4 | `00014` | `0o3153` | пустой |

Поэтому в каждой деке ровно два различных значения среди `x1,y1,x2,y2`.
Все деки побайтно совпадают с `verify/C1-line.b6` кроме строк 34 и 36
(две строки `CALL MOVE`): то же число строк (45 плюс завершающий перевод
строки), те же имена `C1LINE`, тот же `*name`, та же мощность `MOVE`/`PLOT`
(2 пары), тот же `PRINT`/`FORMAT`.

Следствие: при двух различных значениях `A` и `B` приращения координат могут
быть только `0`, `+d` или `-d` (`d = B - A`). У основного штриха `P1 -> P2`
достижимы только наклоны `0` (горизонталь), бесконечность (вертикаль), `+1` и
`-1`. Промежуточных наклонов при сохранении адреса получить нельзя: `d06` и
`d07` это предельные случаи (вертикаль и горизонталь), а не наклоны 5:1 / 1:5.

### Попытка замкнутого контура (d04)

Дека с четырьмя парами `MOVE`/`PLOT` (прямоугольник) была проверена отдельно:
`NPLOT=4`, `frames=4`, но кросс-ссылка дала `*PDEVXY* C 03155`, а `benson.svg`
содержал 0 элементов `<path>` (кадры декодировались в `(0,0)`). Увеличение
числа операторов тоже сдвигает адрес. Поэтому `d04-rectangle.b6` использует
2 пары и рисует разомкнутый контур из двух сторон (низ плюс правая сторона),
а не замкнутый прямоугольник.

## Как получается растр из кадров

- Один `CALL PLOT()` это один кадр с пером DOWN в точке, заданной предыдущим
  `MOVE`. Начальная позиция пера `(0,0)`, перо поднято.
- Движение к точке кадра идёт сначала по X, затем по Y (целые шаги 0.1 мм).
  Поэтому наклонная линия в SVG это L-образная ломаная, а не прямая:
  `du_decode_stream_coords()` в `dispak/extra.c` эмитирует `+X/-X` перед `+Y/-Y`.
- После каждого кадра перо поднимается и делает шаг вперёд-назад, чтобы
  рендерер `plotter.cpp` сбросил накопленный `path`. Итого 2 элемента `<path>`
  на деку: первый соединитель от начала координат к `P1`, второй основной
  штрих `P1 -> P2`.
- SVG-координата `Y = maxy - ben.y`, где `maxy = max(y1,y2)`, ось Y перевёрнута.
  Точки с одинаковым направлением схлопываются алгоритмом `is_collinear()`.
- Размер SVG: `width = max(x1,x2) + 2`, `height = max(y1,y2) + 1`
  (дополнительная единица по X появляется из-за шага вперёд-назад при
  поднятом пере).
- Все координаты лежат в `0..200` шагов (0..20 мм), что далеко внутри лимита
  `ben.limit_x=5000`, `ben.limit_y=7500` (50 x 75 см). Выхода за лимит нет.

## Что считается прохождением

По две прогонки на деку; обе должны дать:

- `NITI: summary` и `КОНЕЦ ЗАДАЧИ`, ни одного `ОШ`/`ERR`/`ОТСУТСТВУЕТ`;
- кросс-ссылку `*PDEVXY* C 03147` (адрес не сдвинулся);
- непустые `benson.out` и `benson.svg`, SVG начинается с `<?xml` и содержит
  `<path`;
- одинаковые SHA256 `benson.out` и `benson.svg` в обоих прогонках.

При отсутствии артефактов раннер печатает FAIL и причину, а не выдуманные
значения. Точные хэши и размеры фактического прогона приведены в `RESULTS.md`.
