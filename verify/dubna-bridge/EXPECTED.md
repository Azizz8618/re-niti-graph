# Ожидаемое содержимое calcomp.out и calcomp.svg

Статус: это контракт для ещё не собранного бэкенда, а не протокол
реального прогона. На момент подготовки `run.sh` останавливается с FAIL,
потому что в бинарнике dispak нет `DUBNA-PLOT`, `calcomp.out` и `proven`.
Все числа ниже, кроме SHA `plot.dat`, это ожидания, которые нужно
подтвердить первым честным прогоном после сборки.

## 1. Формат calcomp.out

`calcomp.out` это сырой поток байтов, который Дубна отправляет на
 Calcomp (`plotter.cpp:398-418`, `e57.cpp:42-46`). Кодирование шага:

| Бит (восьм.) | Значение |
|---|---|
| `01` | `-X`, шаг влево |
| `02` | `+X`, шаг вправо |
| `04` | поднять перо |
| `010` | опустить перо |
| `020` | `+Y`, шаг вверх |
| `040` | `-Y`, шаг вниз |

Ожидаемая структура потока для обеих дек:

1. Первый байт `04`, то есть поднять перо перед перемещением в начальную
   точку. Это требование к мосту, а не наблюдение: проверяется после сборки.
2. Далее идут байты шагов `01`, `02`, `020`, `040`, перемещающие перо в
   позицию, определённую кадрами `plot.dat`. Команда `010` (перо вниз)
   включается перед рисованием линии.
3. Повторные `04` и `010` допустимы на границах фрагментов. Парсинг
   `plotter.cpp:398-418` обрабатывает их как смену состояния пера, а не как
   движение: байт без `dx`/`dy` не порождает точку.
4. Байты, у которых одновременно выставлены `01` и `02` или `020` и
   `040`, дают `dx = 0` или `dy = 0` соответственно. Такой байт не считается
   шагом по этой оси (`plotter.cpp:398-418`).

Для C1-line (`CALL MOVE(10,10)`, `PLOT`, `MOVE(110,110)`, `PLOT`) ожидается
монотонная последовательность шагов `+X` и `+Y` без хаотичных `-X`/`-Y`.
Для t02-frame (`NITI: summary ... words=64`) ожидается поток, полностью
определённый единственным кадром из 64 слов. Точное число байтов заранее
не фиксируется: оно зависит от выбранного отображения `proven` и должно
быть записано сюда после первого прогона.

Запрещено требовать, чтобы `calcomp.out` совпадал с
`tests/expect_calcomp_output.bin`. Причина в разделе 4.

## 2. Формат calcomp.svg

Файл создаётся функцией `Plotter::calcomp_convert_svg()`
(`plotter.cpp:318-391`) из того же потока байтов. Ожидаемые признаки:

```
<?xml version="1.0" encoding="utf-8" ?>
<svg xmlns="http://www.w3.org/2000/svg" ... width="W" height="H" viewBox="0 0 W H">
<g fill="none" stroke="black" stroke-linecap="round" stroke-width="1">
<path d="M x y x y ..."/>
...
</g>
</svg>
```

Дополнительные инварианты по коду:

- `width`/`height` равны `maxx + 1 - minx` и `maxy + 1 - miny`, координаты
  нормализуются через `x - minx` и `maxy - y` (SVG считает ось Y сверху);
- `<path>` выводится только если накоплено не менее двух точек, поэтому
  одиночные точки и пустой поток не дают `<path>`;
- коллинеарные промежуточные точки отбрасываются (`is_collinear`),
  поэтому число вершин в `<path>` меньше числа шагов;
- временных меток, случайных чисел и номеров процесса в генераторе нет,
  значит при байтово одинаковом `calcomp.out` SVG детерминирован;
- префикс имени файла `calcomp` означает, что при включённой нумерации
  страниц имя файла может стать `calcomp1.svg`, `calcomp2.svg` и так далее
  (`append_suffix`, `plotter.cpp:83-90`). Раннер ожидает `calcomp.svg` для
  обоих дек: смена страницы в них не требует 여러 страниц вывода.

## 3. Проверка детерминированности

```
KEEP_WORK=1 ./verify/dubna-bridge/run.sh
```

Раннер прогоняет каждую деку дважды в отдельных подкаталогах с одним и тем
же окружением (`BESM6_NITI_DECODE=proven`, `BESM6_DUDKA_TEST=1`) и считает
SHA256 трёх файлов: `plot.dat`, `calcomp.out`, `calcomp.svg`. Тест проходит,
только если все три SHA совпали между прогоном 1 и прогоном 2.

Дополнительная ручная проверка с сохранённым каталогом:

```
sha256sum $WORK/run/C1-line-r1/calcomp.out $WORK/run/C1-line-r2/calcomp.out
sha256sum $WORK/run/C1-line-r1/calcomp.svg $WORK/run/C1-line-r2/calcomp.svg
cmp $WORK/run/C1-line-r1/calcomp.out $WORK/run/C1-line-r2/calcomp.out
```

Что важно:

- Сравнение делается внутри одной сборки dispak. Между разными сборками
  детерминированность не гарантируется и не требуется.
- Стабильность `calcomp.out` не отменяет проверку `plot.dat`. Оба файла
  должны быть стабильными, и SHA `plot.dat` должен остаться прежним.
- Если мост пишет `calcomp.svg` с датой или порядковым номером, тест должен
  упасть: значит используемый генератор отличается от `plotter.cpp`.

## 4. Почему нельзя требовать совпадения с эталоном Дубны

Эталоны `tests/expect_calcomp_output.bin` и `tests/expect_calcomp.svg`
получены из дек `examples/grafor/*.dub`. Например, `calcomp.dub` рисует
строку `Calcomp` через `CALL PAGE(14.0, 10.0, 'PAGE', 4, 0)`,
`CALL LIMITS(0.0, 14.0, 0.0, 10.0)` и `CALL SYMBOL(0.1, 3.5, 3.3, ...)`.
Наши деки рисуют прямую линию через PERSO (`C1-line.b6`) или проверяют
низкоуровневую запись одного кадра (`t02-frame.b6`). Разные программы и
разные координаты дают разные потоки шагов. Аналогичный случай уже
описан в `docs/NITI-CALL-DETAILED.md:582`: разница между нативным вызовом
и C1-line объясняется разными программами, а не несовместимостью протокола.

Кроме того, `plot.dat` это формат НИТИ/БЕНСОН: 64 слова на кадр,
восемь шестибитных групп на строку. CalComp Дубны это байтовый поток.
Это разные устройства и разные уровни представления. Эталон Дубны
проверяет, что `plotter.cpp` правильно принял байты от ЭК `*57`. Наш тест
проверяет другое: что мост доставил в тот же приёмник байты, полученные из
`plot.dat`, и сделал это воспроизводимо.

## 5. Что проверяет раннер, а что нет

| Проверка | Есть в run.sh | Комментарий |
|---|---|---|
| Маркеры готовности моста в бинарнике | да | при отсутствии честный FAIL, exit 3 |
| Строка `NITI: summary ...` | да | вместе со счётчиками кадров и слов |
| Прежний SHA `plot.dat` | да | C1 и t02, полные значения |
| Строка `DUDKA: DUBNA-PLOT device=calcomp` | да | наличие в логе |
| Наличие и непустота `calcomp.out`, `calcomp.svg` | да | |
| SHA между двумя прогонами | да | для трёх файлов сразу |
| Первый байт `04` в `calcomp.out` | нет | это контракт моста, проверяется вручную после сборки |
| Совпадение с `expect_calcomp_output.bin` | нет | неприменимо, см. раздел 4 |
| Запуск `ctest` | нет | его запускает lead |
